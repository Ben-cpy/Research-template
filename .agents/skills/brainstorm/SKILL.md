# 研究问题与 idea

先明确谁在什么条件下遇到什么可观测困难，再考虑方法，不要求用户先给 idea。
研究前按项目 `AGENTS.md`、`docs/workflow.md` 读取 context 并核验已有证据；
共同的交付要求见 `context/output_contract.md`，此处只补充选题判断。

## 如何收敛

- 从实际现象、反例、条件变化和相关工作未解释的部分提出问题；没有证据时标为假设，不虚构缺口。
- 比较机制上不同的解释，而非同一方法的参数变体；为候选解释指出能区分它们的观察。
  检查简单工程措施或测量偏差是否足以解释现象，不强求固定数量的假设。
- 依据问题影响、现有证据缺口、可区分性与验证成本选择方向；说明最先检查什么、结果如何改变决策。
  优先选择能排除关键解释的小检查，能推导时先推导，不因容易跑就优先。
- 核查原始论文或官方资料及实际阅读范围，区分作者宣称、实证设置、本项目推断和可借鉴机制。
  “没人做过”不是充分价值依据，前作有局限也不等于方向无效。
- 方法 idea 要对应具体困难、预期机制和失效条件；允许结论是暂不值得推进，不强迫每个问题产生方法。

## 交付

先给判断，再按请求深度说明问题与价值、证据缺口、竞争解释、最小验证和继续或放弃的条件。
只展开影响当前判断的内容，不要求逐栏填表；未知项说明影响，只追问会改变方向的问题。
问题明确且需要量化协议时使用 `exp-design`。讨论本身不启动实验，已授权的探索按 workflow 继续。

## 简例（教学假设，非项目结论）

Agent 在工具超时后重复写入，候选解释包括首次写入成功但响应丢失，以及重试时目标对象变化。
先核对调用参数与业务状态时间线，检查能否区分两者；若简单状态查询已足够，
优先评估该基线。研究价值取决于剩余失效及其影响，不能仅凭“增加检查节点”宣称贡献。
