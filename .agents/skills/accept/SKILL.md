# 实验结果验收

判断已有证据支持什么、还缺什么，以及是否继续。遵守项目 `AGENTS.md`，以实际运行记录和运行前方案为依据。

## 回答约束

- 开头给出“支持 / 不支持 / 证据不足”的判断及理由；按请求控制篇幅，不固定对话行数或附逐条自检。
- 区分原始实测、用户转述、文献、推导与推断；关键数字附证据位置，写清单位、条件、基线和计算口径。没有原始文件时明确尚未独立核查。
- 按冻结指标、预测与判定条件验收，不能为适配结果修改阈值、挑选有利设置或隐藏失败结果。
- 历史实验没有事前预测时标为“探索性结果”；后续假设另行设计验证，不能事后补预测并称已验证。
- 缺结果时列出验收所需证据；部分结果可以部分验收，未能核查的判断写 `TBD`，只询问影响判断的问题。

## 验收必须说明

| 项目 | 回答要求 |
| --- | --- |
| 判断与对象 | 对应哪个实验、哪次运行、哪条主张；支持、不支持或证据不足的依据 |
| 预测与实测 | 对照原指标、基线与条件报告实际结果、重复测量的波动；派生指标写明公式 |
| 覆盖与公平性 | 哪些设置完成、缺失或失败；对照是否匹配数据、环境、预算与质量条件 |
| 证据与异常 | 核查方案、实际配置、原始日志和汇总是否一致；异常如何影响判断，未核查项明确列出 |
| 边界与下一步 | 能支持和不能支持什么；继续、补测、缩小主张或停止的理由；否定时说明仍可能成立的条件 |

不要混合不同运行版本的结果；质量条件未满足时，不能仅凭效率优势宣称方案成功。
证据核查只报告实际完成的检查及产物位置；单看汇总表不能声称复现或独立验证已经通过。
需要定位异常时，先缩小到最小输入；建议补测不自动启动实验，已授权的多阶段任务可继续执行。

讨论时直接回答；用户要求保存正式验收时，将报告写入对应运行目录的 `acceptance.md`，链接原始证据。
验收正式实验后，在 `paper/exp_design.md` 更新该固定编号的状态、结果摘要和结论；`paper/plan.md` 只引用编号。保留原始结果与冻结方案。

## One-shot：集合查询

示例只教结构；以下输入是虚构教学数据，未运行，也不存在可据此引用的真实日志。

**输入：** 原方案规定：1000 次查询时，答案一致且 5 次配对测量全部更快，才暂时支持集合方案。现在列表中位耗时 2.0 ms，集合 1.0 ms，5 次都更快，答案一致；1 次和 100 次查询还没测。未提供原始文件。能说集合更好吗？

**输出：**

> 按你提供的数据，暂时支持“1000 次查询条件下集合方案更快”；完整实验仍是部分完成，原始证据尚未核查。
>
> **预测对照：** 答案一致，5 次配对测量均更快，满足原方案的初筛条件。[用户提供的教学数据]
> **量化结果：** 列表中位耗时 2.0 ms，集合 1.0 ms；加速比为基线中位耗时 / 集合中位耗时 = 2.0 倍。这是两个中位数之比，不是配对加速比的中位数。[按输入计算]
> **覆盖与证据：** 1 次和 100 次查询未完成；缺原始计时、配置和环境，尚不能确认两方案输入一致、计时包含集合构建成本，也不能核查波动。
> **结论边界：** 只能暂时支持所报条件下的效率优势，不能声称集合总是更好，也不能把初筛结果当作统计显著性的证明。
> **下一步：** 先核对原始证据，再补齐剩余设置；若只关心 1000 次查询，可以缩小主张并注明未覆盖范围。核查前不把该结果标为最终验收通过。
